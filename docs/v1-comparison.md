# Comparison - v1 Diagrams vs. Real Code

> **Note.** This document records the state of `docs/description.md` *before* the
> adjustments. The omissions pointed out in section 3 (for example, the order of
> the snapshot save and the moment the whitelist is loaded) applied to the
> description of that time; `docs/description.md` was updated afterwards with the
> missing information.

This document compares `docs/diagrams/structural-v1.mmd` and
`docs/diagrams/sequence-v1.mmd` - produced only from `docs/description.md`,
without access to the code - with the real source code in `D:\PendriveAgent`
(`agent.py`, `tools.py`, `history.py`). The diagrams **were not corrected** in
this step; the goal here is only to assess, with proof in code, where the
inference made from the description alone was right, where it was wrong, and
where the description itself did not give enough information to decide.

## 1. What was inferred correctly (with justification)

**The three modules run in the same process/container.** Both diagrams group
`agent.py`, `tools.py` and `history.py` inside a single boundary ("Agent
Process"). This is correct: `agent.py` imports the functions of `tools.py` and
`history.py` directly (`from tools import list_processes,
list_network_connections, list_startup_items` and `from history import
load_latest_snapshot, save_snapshot, diff_snapshots`, lines 31-32), so there is
no process or machine separation between them - it is all one running Python
interpreter.

**HTTP endpoint and verb for the inference server.** The structural and the
sequence diagrams use `POST /v1/chat/completions`. This matches `call_llm()` in
`agent.py` exactly, which builds the request to `f"{host}/v1/chat/completions"`
with `method="POST"`.

**Order of the three collections.** The sequence diagram shows `Agent` calling
`Tools` three times, in this order: processes, network connections, startup
items. It is exactly the order in `run_agent()`: `list_processes(...)` followed
by `list_network_connections()` followed by `list_startup_items()`.

**Two distinct calls to `History` to get the previous snapshot and compute the
diff.** The diagram models this as two separate interactions (`ask for previous
snapshot` and then `compute difference`). This corresponds faithfully to
`run_agent()`, which calls `load_latest_snapshot()` and then passes the result to
`diff_snapshots(previous, processes, connections, startup)` as two distinct
function calls.

**No whitelist check for network connections.** Neither diagram connects the
network connection collection to the `Whitelist` container/participant. This is
right: `list_network_connections()` in `tools.py` makes no reference to
`WHITELIST_PROCESSES` or `WHITELIST_STARTUP` - only processes and startup items
are compared with the whitelist.

**The LLM summary is not persisted in the history - only the raw data.** The
sequence diagram labels the final step "save collected snapshot", not "save the
report". This is right: `save_snapshot(processes, connections, startup_items)`
in `history.py` (lines 39-52) writes only `timestamp`, `processes`,
`connections` and `startup_items` to the JSON - the text generated by the LLM
(`answer`) is never passed to that function nor written anywhere; it is only
printed to the terminal.

**`build prompt` as a self-message on `Agent`, not a call to another
participant.** The sequence diagram represents prompt building as
`Agent->>Agent: build prompt...`. This is consistent with the code:
`build_prompt()` is a function defined inside `agent.py` itself and called
locally by `run_agent()` - it belongs to neither `tools.py` nor `history.py`.

**The diff computation does not touch the scans directory.** The sequence
diagram draws no interaction between `History` and `ScansDir` during the
"compute difference" step. This is correct: `diff_snapshots()` in `history.py`
(lines 67-89) operates entirely in memory over the data already loaded
(`previous`) and the current data received as parameters - it does no disk reads
or writes.

## 2. What diverged from the real system or was invented (with proof)

**Sequence error: the snapshot is saved BEFORE calling the LLM, not after.** The
sequence diagram places `Agent->>History: save collected snapshot` as the last
block of the whole journey, after `Agent->>LLM: POST /v1/chat/completions` and
after `Agent->>User: prints scan summary`. This is factually wrong. In
`agent.py`, inside `run_agent()`, the real order is:

```python
previous = load_latest_snapshot()
diff = diff_snapshots(previous, processes, connections, startup)

snapshot_path = save_snapshot(processes, connections, startup)   # <- saved HERE
print(f"  -> snapshot saved at: {snapshot_path}")

prompt_data = build_prompt(processes, connections, startup, diff)
...
response = call_llm(host, model, messages)                       # <- LLM called AFTER
```

(lines ~121-138 of `agent.py`). The snapshot is written to disk *before* the
prompt is built and *before* any call to the inference server. If the LLM call
fails or hangs, the snapshot is already saved - something the diagram, by placing
the save last, completely hides. This was not an acceptable simplification: it is
an inversion of the real order of the system's side effects.

**Mechanism error: the whitelist is not queried "live" during collection - it is
loaded once, at module import.** The sequence diagram draws `Tools->>Whitelist:
query known names` / `Whitelist-->>Tools: known names` as a runtime message
exchange, and repeats it twice (once after collecting processes, once after
collecting startup items), as if it were a one-off query on each collection.
That is not what the code does. In `tools.py`:

```python
WHITELIST_PROCESSES, WHITELIST_STARTUP = load_whitelist()   # line 36, module level
```

This line runs **only once**, at the moment `tools.py` is imported - even before
`run_agent()` starts collecting anything. From there on, `list_processes()`
(line 56: `name.lower() in WHITELIST_PROCESSES`) and `list_startup_items()` (line
106: `any(w in name for w in WHITELIST_STARTUP)`) merely test membership against
*sets* already loaded in memory, inside `tools.py` itself - there is no second
read of the file, nor a "message" sent to an external participant called
`Whitelist` during collection. The diagram treats as a repeated runtime
interaction something that is actually an import-time effect, executed once and
cached.

No purely invented components (with no basis in the code) were found in either
diagram - the two errors above are **timing/event order** errors, not the
existence of containers or modules that do not exist in the real system.

## 3. What the description did not cover and caused the assumption

**Order between saving the snapshot and calling the LLM.** `docs/description.md`
describes the responsibilities of `agent.py` as a list ("triggers the
collections, asks for the comparison, builds the prompt, calls the LLM, prints
the summary") that **does not even mention** the snapshot-saving step in that
sequence - it only appears, in isolation, in the description of `history.py`'s
responsibilities. Without an explicit order, the task statement itself ("...up
to the report saved in the history") is what guided the assumption that saving
would be the last step. This gap in the description is the direct cause of the
error pointed out in section 2, item 1.

**Moment the whitelist is loaded.** `docs/description.md` says only that
`tools.py` "is responsible for loading the whitelist file and flagging, on each
collected item, whether it is recognized as expected" - a sentence about
*responsibility*, not about *when* the loading happens (once, per run, per item).
This omission is the direct cause of the error pointed out in section 2, item 2:
in the absence of that information, a live query per collection was assumed
(incorrectly), instead of a single load into memory.

**Existence of a "User" actor.** The description never names a "user" or
"operator" as part of the system - it only mentions, in passing, that `agent.py`
"reads the command-line arguments" and that the final summary is "aimed at a
non-technical person". With no such container/actor explicitly described, it was
invented in both diagrams to close the journey end to end. The code confirms it
makes sense to model that entity (there is `argparse` reading and `stdout`
printing), but it is not a name taken from the description, rather an inference
to fill the absence of an explicit entry/exit point in the text.

**Actual structure of the LLM request.** The description speaks of an "HTTP call
to the inference server" generically, without detailing that the request body
carries two distinct messages (fixed system prompt + user prompt with the
collected data) inside the same JSON payload. This lack of detail led to
simplifying the interaction as a single generic arrow `POST /v1/chat/completions
(prompt)`, hiding that, in practice, several messages are composed before
sending.

**Whether the diff computation touches the disk.** The description does not state
explicitly that `diff_snapshots` operates only in memory - this had to be
inferred (and, in this case, the inference matched the code). But it is important
to record that it was an assumption, not information given by the description:
the text of `docs/description.md` speaks of "computes the difference between the
current state and that previous snapshot" without detailing whether this
involves additional I/O. The diagram was right through reasoning (the comparison
would not need to re-read anything not already loaded in the previous step), not
because the description guaranteed that behavior.
